# Грейдер проекта «Бекенд для интернет-магазина»

Это тесты Хекслета, которыми проверяется решение. Студент их **видит и запускает сам**: `__data__/spec.yml` отдаёт каталог в `artifacts`. Так сделано намеренно — падение теста здесь это ответ его API, а не устройство интерфейса, который написали мы.

Тот же набор гоняется против эталонного решения из `code/` при `make ci` — это доказательство проходимости.

## Как устроено

Тесты — **чистый black-box на уровне браузера**: они ходят по предоставленному фронтенду и не делают ни одного прямого запроса к API. Всё, что нужно для сценария — регистрация, наполнение корзины, — готовится через интерфейс.

Это не значит, что проверяется фронтенд. Фронтенд одинаковый у всех и заведомо рабочий, поэтому единственная причина падения — ответ API: не тот статус, не та форма тела, не тот набор данных.

Следствия, важные для чтения падений:

- **Селекторы вместо текста.** Состояния читаются `data-`атрибутами: `data-available` у доступности товара, `data-status` у статуса заказа. Видимый текст не сверяется нигде.
- **Навигация через интерфейс.** Корневой адрес отдаёт главную, каталог живёт на своей странице. Прологу, которому нужен каталог, тест открывает `/` и жмёт `nav-catalog`. Напрямую открываются только три адреса из раздела «Адреса страниц» чеклиста: `/`, `/cart`, `/account`.
- **Никаких конкретных товаров.** Каталог наполняет студент, тесты опираются только на контракт на данные из `__data__/checklist.md`: минимум три категории, двенадцать товаров, минимум один недоступный, цены разного порядка, минимум две страницы, минимум два промо-блока. Тест поиска берёт фрагмент названия у уже показанного товара, а не ищет заранее известное слово.
- **Уникальный email на каждый прогон.** База между прогонами может не пересоздаваться, поэтому регистрация с фиксированным адресом законно упала бы с «email занят».

## Что именно проверяет каждый класс кейсов на стороне API

| Кейс | Требование к API |
|---|---|
| промо на главной | `GET /api/promos` отдаёт блоки с **вложенным** товаром |
| каталог, фильтры, страницы | `GET /api/products` фильтрует и пагинирует **на сервере**, `meta` честный |
| карточка | `GET /api/products/{id}` по тому же id, что в списке; 404 на неизвестном |
| корзина | `GET /api/products/{id}` переживает перезагрузку страницы (в браузере лежат только id и количество) |
| регистрация и вход | `POST /api/users`, `POST /api/session`, `GET /api/me`, `DELETE /api/session`; 409 на занятом email, 401 на неверном пароле |
| кабинет анонимом | `GET /api/me` отвечает 401, а не 200 с пустым телом |
| оформление | `POST /api/orders` считает итог сам, требует адрес при доставке, отказывает целиком при недоступном товаре |
| кабинет | `GET /api/orders` отдаёт только заказы текущего пользователя со снимком цен |

## Почему APP_URL, а не BASE_URL

`BASE_URL` зарезервирован Vite и Vitest — они затирают его на `/`. Адрес приложения приходит в `APP_URL`, и **фолбэка нет**: без переменной конфиг падает с понятной ошибкой, а не гоняет тесты против случайного адреса.

`docker compose` задаёт `APP_URL: http://online-store.test:8080`. Домен из зарезервированной зоны `.test` выбран специально: Chromium не апгрейдит такие адреса с http на https, в отличие от `.dev` или `.app`.

## Артефакты при падении

Проверку решения гоняет GitHub Action `Hexlet/project-action`. Он собирает артефакты по glob `tmp/artifacts/*/**` и публикует их как GitHub-артефакт **`test-results`**.

`preserveOutput: 'failures-only'` — для прошедших тестов каталог остаётся пустым. При падении там появляются `trace.zip` (`npx playwright show-trace`), скриншот и видео. HTML-репорт кладётся туда же (`tmp/artifacts/playwright-report/index.html`) — иначе он остался бы на раннере.

Там же, в `tmp/artifacts/contract/openapi.yaml`, оказывается **эталонная спецификация API**: её кладёт цель `make test`. Это подсказка при разборе падения — сверить свою форму ответа с ожидаемой.

## Названия кейсов — только короткий ASCII

Имя каталога артефактов Playwright собирает из названия теста: `<файл>-<название с пробелами через дефис>` + `-<проект>`. Кириллица не санитизируется и уезжает в имя файла как есть. Хуже другое: если `<файл>-<название>` длиннее **60 символов**, Playwright вырезает середину и вставляет огрызок sha1 — имя перестаёт сопоставляться с тестом.

Поэтому названия тестов английские и укладываются в лимит (бюджет: 60 минус длина имени файла и дефис — для `catalog` это 51 символ). Пунктуацию не используем: скобки, кавычки, слеши и запятые склеиваются в дефисы и дают `--` в имени каталога.

## Запуск

```sh
make ci                                   # полный прогон: сборка, поднятие app, тесты
APP_URL=http://localhost:8080 npm test    # против локально запущенного приложения
```

Один воркер и один браузер — не перестраховка: тесты меняют состояние общей базы (регистрируют пользователей, создают заказы), и параллельный прогон сделал бы результат недетерминированным.
